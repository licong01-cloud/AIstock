## 三、每次选股的临时文件生成流程

### 3.1 流程概述

每次选股执行时，推理引擎按以下步骤生成临时文件：

1. **创建临时目录**（`inference_engine.py` 第816行）：`tmp_dir = Path(tempfile.mkdtemp(prefix="aistock_inf_"))`
2. **切换工作目录**（第819行）：`os.chdir(tmp_dir)`
3. **生成 `daily_pv.h5`**（第822-832行）：将从数据库获取的OHLCV行情数据写入H5文件
4. **生成 `static_factors.parquet`**（第838-1036行）：从数据库获取基本面和资金流数据，计算预计算字段后写入parquet文件
5. **执行因子计算**（第1042-1047行）：因子代码从临时目录读取上述两个文件
6. **清理临时目录**（第1100行）：`shutil.rmtree(tmp_dir, ignore_errors=True)`

### 3.2 因子代码如何读取文件

以当前因子 `factor.py` 为例（第8行和第21行）：

```python
df = pd.read_hdf("daily_pv.h5", key="data").sort_index()
static_df = pd.read_parquet("static_factors.parquet", columns=required_static_cols).sort_index()
```

因子代码使用**相对路径**读取文件，依赖于推理引擎将工作目录切换到临时目录。这是RDAgent因子的标准接口约定——因子代码不接受参数，通过文件系统读取数据。

### 3.3 为什么必须生成临时文件

RDAgent生成的因子代码（`calculate_xxx()` 函数）遵循固定接口规范：
- **无参数**（`inference_engine.py` 第1042-1044行检查 `len(sig.parameters) == 0`）
- **从当前目录读取 `daily_pv.h5` 和 `static_factors.parquet`**
- **返回 DataFrame**

如果不生成这些文件，因子代码将因 `FileNotFoundError` 而失败。**在不修改因子代码的前提下，必须生成这些临时文件。**

- 如果某因子需要超过63个交易日（90自然日）的行情数据，`daily_pv.h5` 中的数据不够，因子计算结果中对应行将产生 `NaN`（如滚动窗口不足时 `min_periods` 不满足）
- 如果某因子需要超过180自然日的基本面/资金流数据，`timescaledb_adapter.py` 第111-115行会强制截断到180天，并输出 `WARNING` 日志，但**不会报错**
- 因子代码本身可能因数据不足而返回全 `NaN` 的结果，推理引擎不会因此报错，但模型预测结果将不准确

### 5.1 单次选股数据量估算

### 5.2 性能消耗分解

每次选股的主要性能消耗环节：

| 环节 | 操作 | 预估耗时 |
|-----|------|---------|
| ① 数据库查询-行情 | 查询 `market.kline_qfq`，约34万行 | 2-5秒 |
| ② 数据库查询-基本面 | 查询 `market.daily_basic`，约34万行 | 2-5秒 |
| ③ 数据库查询-资金流 | 查询 `market.moneyflow_ts`，约32万行 | 2-5秒 |
| ④ 预计算字段计算 | 滚动窗口、分组计算等 | 1-3秒 |
| ⑤ 写入daily_pv.h5 | ~15.8MB HDF5写入 | 0.5-1秒 |
| ⑥ 写入static_factors.parquet | ~79MB Parquet写入 | 1-3秒 |
| ⑦ 因子代码读取文件 | 读取H5+Parquet | 1-3秒 |
| ⑧ 因子计算 | 因子逻辑本身 | 0.1-1秒 |
| ⑨ 模型预测 | LGB/PyTorch推理 | 0.1-1秒 |
| ⑩ 临时目录清理 | 删除~95MB文件 | 0.1-0.5秒 |
| **合计** | | **约10-27秒** |

### 5.3 性能瓶颈分析

1. **数据库查询（①②③）**：占总耗时约50-60%，是最大瓶颈。每次查询约34万行数据，涉及全量股票池的90天数据
2. **文件I/O（⑤⑥⑦）**：占总耗时约20-30%。写入和读取约95MB临时文件
3. **计算（④⑧⑨）**：占总耗时约10-20%。预计算字段和因子计算本身

### 5.4 磁盘I/O影响

- 每次选股产生约95MB临时文件的写入和读取
- 使用系统临时目录（通常在系统盘），频繁写入可能影响SSD寿命
- 并发选股时，多个临时目录同时写入可能造成I/O竞争

## 七、优化方案评估

### 7.1 约束条件

- **不修改因子代码逻辑**：因子代码必须保持原样，通过文件系统读取 `daily_pv.h5` 和 `static_factors.parquet`
- **数据必须来自最新行情**：禁止使用历史快照文件
- **不使用未经明确要求的兜底方案**

### 7.2 方案A：补全缺失的预计算字段（推荐）

**问题**：当前推理引擎中预计算字段不完整，导致部分因子无法正常执行。

**方案**：在 `inference_engine.py` 的预计算字段计算区域（第884-955行），补充所有RDAgent预计算因子文档中定义的字段。

需要补充的字段及其计算公式（均基于已从数据库获取的 `db_*` 和 `mf_*` 原始字段）：

```python
# daily_basic_factors
value_pe_inv = 1 / db_pe_ttm  (db_pe_ttm=0时为NaN)
value_pb_inv = 1 / db_pb  (db_pb=0时为NaN)
size_log_mv = np.log(db_circ_mv)  (db_circ_mv<=0时为NaN，回退db_total_mv)
liquidity_turnover = db_turnover_rate
liquidity_vol_ratio = db_volume_ratio

# moneyflow_factors（完整版）
mf_total_net_vol = mf_net_vol
mf_total_net_vol_ratio = mf_net_vol / volume
mf_main_net_amt = (mf_lg_buy_amt + mf_elg_buy_amt) - (mf_lg_sell_amt + mf_elg_sell_amt)
mf_main_net_vol = (mf_lg_buy_vol + mf_elg_buy_vol) - (mf_lg_sell_vol + mf_elg_sell_vol)
mf_main_net_amt_ratio = mf_main_net_amt / amount
mf_main_net_vol_ratio = mf_main_net_vol / volume
mf_elg_net_amt = mf_elg_buy_amt - mf_elg_sell_amt
mf_elg_net_vol = mf_elg_buy_vol - mf_elg_sell_vol
mf_elg_net_amt_ratio = mf_elg_net_amt / amount
mf_elg_net_vol_ratio = mf_elg_net_vol / volume
mf_elg_share_in_main_vol = mf_elg_net_vol / mf_main_net_vol

# 5D/20D滚动聚合
mf_total_net_amt_5d, mf_total_net_amt_20d
mf_main_net_amt_5d, mf_main_net_amt_20d
mf_elg_net_amt_5d, mf_elg_net_amt_20d
mf_total_net_amt_ratio_5d, mf_total_net_amt_ratio_20d
mf_main_net_amt_ratio_5d（已有）, mf_main_net_amt_ratio_20d
mf_elg_net_amt_ratio_5d（已有）, mf_elg_net_amt_ratio_20d
```

**优点**：
- 所有RDAgent因子均可正常执行
- 不修改因子代码
- 计算公式简单，性能开销极小（均为向量化运算）

**缺点**：
- 需要维护预计算字段列表与RDAgent侧保持一致

### 7.3 方案B：内存文件系统替代磁盘I/O

**问题**：每次选股写入约95MB临时文件到磁盘。

**方案**：使用内存文件系统（如Python的 `io.BytesIO` 配合 `tempfile` 的内存后端）或 RAM disk 来存储临时文件。

**分析**：
- 在不修改因子代码的前提下，因子代码使用 `pd.read_hdf("daily_pv.h5")` 读取文件，这要求文件必须存在于文件系统中
- Python的HDF5库（h5py/PyTables）不支持从 `BytesIO` 读取
- 因此，**在不修改因子代码的前提下，无法完全消除磁盘I/O**
- 可以将临时目录指向更快的存储（如NVMe SSD），但这属于运维层面优化

### 7.4 方案C：缓存机制减少重复查询

**问题**：如果短时间内多次选股（如不同task的因子），每次都重新查询数据库和生成文件。

**方案**：对同一交易日的数据库查询结果进行缓存，多次选股复用同一份数据。

**分析**：
- OHLCV行情数据在同一交易日内不变，可以缓存
- 基本面和资金流数据在交易日结束后不变，可以缓存
- 缓存粒度：以 `(actual_date, universe_hash)` 为key
- 缓存有效期：当日有效，次日自动失效
- 可减少数据库查询次数，但仍需生成临时文件（因子代码约束）

### 7.5 方案D：扩大历史数据窗口

**问题**：当前90天窗口可能不满足某些因子的需求（如20日滚动需要更多前置数据）。

**分析**：
- 20日滚动聚合需要至少20个交易日的前置数据，当前63个交易日足够
- 但如果未来因子需要更长窗口（如60日滚动），90天自然日（约63个交易日）刚好覆盖，安全余量不足
- `timescaledb_adapter.py` 中的180天硬限制是对基本面/资金流数据的保护，当前传入的90天远未触及
- 建议：将行情窗口从90天扩大到120天（约84个交易日），为更长窗口因子提供安全余量
