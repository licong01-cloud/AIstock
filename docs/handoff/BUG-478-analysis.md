# BUG-478 analysis

## Independent root cause

MiniQMT capacity residual is currently a valid terminal-success path: the submit
result gate can return `SUCCEEDED` with reason
`miniqmt_capacity_residual_skipped_and_reconciled`, and post-close
terminalization can return `SUCCEEDED` with audit state
`succeeded_with_capacity_residual`. This is intentional run-state behavior for
funds-only capacity residuals after broker/ledger reconciliation.

The defect is observability: operators and unattended monitoring can read only
the top-level `SUCCEEDED` status and miss that `failed_intents`/capacity
residual intents remain. The existing residual details are nested inside
`reconcile_after_submit.submit_result_gate`,
`qmt_batch_residual_summary`, or `miniqmt_post_close_terminalization`, so clean
success and success-with-capacity-residual are not distinguishable at the
summary/dashboard level.

## Fix plan

- Preserve MiniQMT terminal status decisions exactly as-is.
- Add a canonical `miniqmt_capacity_residual_observability` payload when a
  MiniQMT run is `SUCCEEDED` with capacity residual.
- Surface that payload in run payload top-level fields, scheduler tick result
  summary/processed rows, Simulation Runtime ops API run summaries, strategy
  performance payload, and live dashboard warnings.
- Keep clean `SUCCEEDED` runs free of the residual flag.
- Keep LocalSim untouched.

## Scope note

The initial BUG scope did not include `backend/services/simulation_runtime/ops.py`
or the API/dashboard regression tests. Scope was expanded because the required
run summary/API contract is generated by `SimulationRuntimeOpsService`, not by
`scheduler.py` alone.
