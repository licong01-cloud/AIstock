# QE 自动演进架构与 RDAgent 深度对比及建议补充

本补充文档专门针对您提出的两个核心问题进行解答与分析：
1. **现有架构与 RDAgent 的知识库、演进流程的异同与借鉴。**
2. **本方案与现有 QE 单次实验的关系（是否完全新建）。**

---

## 1. 知识库与演进流程：与 RDAgent 的深度对比及补充建议

我们在设计方案 v3.0 的阶段二（长期知识库/RAG）和工作流时，确实**深度参考了目前 RDAgent 的架构思路**。但 RDAgent 的场景与 QE 的演进场景有本质区别。下面是对 RDAgent 源码实现方式的分析及针对 QE 演进的补充。

### 1.1 RDAgent 现有的知识库 (Knowledge Base) 实现方式分析
RDAgent 在 `rdagent/components/knowledge_management/` 中实现了复杂的经验沉淀机制：
- **Document 维度**：它不仅存储历史组合，更重要的是它存储了“失败的代码（Bug）”以及修复方案，这是为了它的 Coder 角色（从零写代码）服务的。
- **检索方式 (Retrieval)**：RDAgent 使用 ChromaDB 或 FAISS，在生成新代码或分析结果前，将当前上下文 Embedding，通过 Cosine Similarity 寻找历史上类似的错误或成功经验，拼接到 Prompt 中。
- **演进反馈 (Feedback)**：每次执行后，它有一个专门的环节把 `Error Traceback` 和 `Performance Drop` 总结成一段文本，入库作为经验（Experience）。

### 1.2 对 QE 演进知识库的补充建议
RDAgent 的知识库主要是“防代码报错”。而我们 **QE 的演进不写新代码，只做因子和模型的排列组合**。因此，QE 的知识库重点应该完全不同！

**给您的建议（二期实现时应补充到架构中）**：
1. **因子共线性经验池 (Collinearity DB)**：每次 LOOP 回测后，如果发现两个因子组合在一起导致了严重的冗余（如 IC 没升反降），系统自动将这对因子组合标记为“互斥/拥挤”，存入知识库。未来的 Agent 在提议组合时，如果检索到该规则，会主动放弃该组合。
2. **超参敏感度经验池 (Hyper-param Sensitivity DB)**：记录“在某类因子（如纯量价）下，LightGBM 的 `learning_rate` 在什么区间容易过拟合”。
3. **实现路径建议**：在 AIstock 侧无需引入沉重的本地向量模型。可以直接在 PostgreSQL 中使用 `pgvector` 插件（如果您熟悉），或者简单地使用轻量级文本检索。因为“配置组合”的特征相比大段代码，结构化程度高得多。

### 1.3 演进流程的对比与补充
- **RDAgent 流程**：`Propose(提出假设)` -> `Code(写代码)` -> `Execute(执行)` -> `Feedback(审查报错)` -> `Summarize(总结经验)`。
- **QE 演进流程 (我们在 v3.0 的设计)**：`Researcher(提议配置)` -> `Builder(转JSON)` -> `Execute(WSL跑QLib)` -> `Analyst(看结果)` -> `Evaluator(定SOTA)`。

**流程上的补充建议（阶段一即可加入）**：
- **增加“无效探索熔断机制 (Early Stopping)”**：在 RDAgent 中，如果连续几次生成代码都跑不通，任务会抛出错误。我们在 QE 演进中应补充一个熔断规则：如果 SOTA 连续 5 个 LOOP 没有任何更新，或者 Analyst Agent 报告说“各项指标已逼近当前模型极限”，则提前结束该演进任务，而不需要死板地跑完 100 个 LOOP。

## 2. 新方案与现有 QE 实验的关系解答

**问题：** *目前的方案是否完全新建一套新的 QE 演进实验，与目前的 QE 实验完全独立？*

**解答：在业务逻辑上是上层包下层的关系，在代码和数据表层面是“独立拓展，但底层共用单次实验记录”。**

### 2.1 数据库层面的关系（非完全独立，而是包容关联）
- 在我们 v3.0 的设计中，演进任务创建的是 `qe_evolution_tasks`（总任务表）。
- 但是，**每一个具体的 LOOP，本质上都会在底层的单次实验表 (`qe_experiments` 或我们设计的 `qe_evolution_loops`) 中生成一条记录。**
- 这意味着，每一次演进的一个单步（LOOP），与用户目前在“QE组合中心”手动点一下“生成并运行”所产生的结果在**数据格式上是完全同构的**。

### 2.2 API 与代码层面的关系（完全独立分离）
- 我们强烈建议（并在 v3.0 方案中明确）新建 `quantevolver_evolution.py` 和专用路由。
- 为什么？因为目前的 `/experiments` 路由主要处理单次的用户点击、查详情。如果把自动流转状态机（Scheduler）、WebSocket 实时日志推流（SSE）强加进去，目前的控制器代码会迅速膨胀到难以维护。
- **正确姿势**：新建一套“演进控制微服务”，这个微服务在底层会调用单次实验的构建方法生成 `config.yaml`，但是外层的 UI 和 API 完全走新建的 `/quantevolver/evolution/...` 路径。

### 2.3 总结建议
**不要修改现有的单次实验流程，而是将现有的“单次实验”作为底层函数/模块，被“自动演进状态机”调用。**
- 新建的演进页面、演进数据库表是完全独立的。
- 但是演进产生的每一个 LOOP 的产物（`qlib_res.csv`, `.pkl`），其解析逻辑完全复用现有 QE 的底层解析函数。
